Category definition

What is a Human-Agent Collaboration Client?

LicoUp uses Human-Agent Collaboration Client as a product-category term for software that gives a human one visible collaboration surface across AI agents while preserving explicit control over participants, context disclosure, approvals, durable conversation state, and local effects.

Terminology note: this is LicoUp’s public category label, not a claim that every long-term LicoUp collaboration feature is already released.

The problem

Agent runtimes are multiplying faster than the user-facing coordination layer.

A developer may use one coding agent for implementation, another for review, another through an IDE, and another through a local server or structured process protocol. Each runtime can have its own session model, lifecycle events, permissions, history, and transport.

The collaboration problem begins when the human must keep those separate systems coherent: who is participating, which context is visible, which runtime owns a turn, what may leave the device, what was approved, and how the durable conversation survives changes underneath.

Responsibilities

A collaboration client owns the user-facing coordination boundary.

The exact implementation can vary, but the category is defined by a set of responsibilities that are different from model inference or task orchestration alone.

ResponsibilityWhat the client must make explicit
ParticipantsWhich humans and agents are visible members of the conversation, and which agent is currently acting.
Conversation continuityA durable user-facing history and identity that does not silently collapse into one provider-native session.
Context disclosureWhat history, files, tools, or protected content each admitted participant may receive.
Approval and effectsWhich external disclosure or local effect is authorized, for what destination, scope, and purpose.
Heterogeneous adaptersHow different CLI, ACP, RPC, App Server, HTTP, SSE, or other agent interfaces are normalized without pretending they are identical.
Endpoint boundaryWhich private keys, plaintext, runtime state, history, and trust decisions remain under endpoint control.
Evidence and statusWhat actually happened in an agent lifecycle, without inventing states the native runtime did not emit.

What it is not

It is not another name for an AI agent.

Not a model

The client does not need to own the foundation model. Different agents may use different providers or models.

Not a single agent runtime

An agent runtime executes work. A collaboration client can coordinate the human-facing experience across several runtimes.

Not just orchestration

Orchestration answers how work is routed or sequenced. Collaboration also owns participants, conversation state, disclosure, approval, and user-visible authority.

Not a wire protocol

MCP, ACP, A2A, Lico Arc, HTTP, JSON-RPC, and similar protocols can provide interfaces or transport. A collaboration client is the product layer that uses such interfaces.

Why coding agents are a useful example

Claude Code, Codex, Cursor, Copilot, and OpenCode expose different surfaces.

LicoUp’s current generated adapter inventory contains representative targets for Claude Code, Codex, Cursor, GitHub Copilot, and OpenCode. Their target lanes span stream JSON, App Server JSON-RPC, direct CLI, ACP, and loopback HTTP/SSE.

That diversity is the point: the collaboration layer should not force every agent to become the same implementation. It should give the human a coherent conversation and authority model above heterogeneous runtimes.

FAQ

Common distinctions.

Is a Human-Agent Collaboration Client the same as an agent orchestrator?
No. An orchestrator can live inside a collaboration client, but orchestration focuses on workflow execution while the collaboration client owns the human-facing conversation and authority boundary.

Does a collaboration client replace MCP or ACP?
No. Protocols and agent interfaces are inputs to the client. The client needs to preserve their native semantics while presenting one coherent user experience.

Does local-first mean offline-only?
No. Local-first means local and endpoint-controlled state remains a primary authority. Networked and federated collaboration can still exist without making a remote service the sole source of truth.
